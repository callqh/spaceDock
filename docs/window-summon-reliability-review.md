# 当前桌面唤起：故障复盘与统一方案

日期：2026-11-16。状态：诊断结论与待实施方案，不代表已修复或已验收，也不替代已确认需求。

## 后续采纳范围

用户随后批准精简实现：保留两条打开路径、请求内窗口身份和必要状态检查；不实施长期注册表、完整事件追踪和应用专属适配。下文完整方案作为诊断背景保留，当前代码范围以 [architecture.md](architecture.md) 为准。

## 结论

目前不是单一的“微信与 Lark 不兼容”。已确认的结构性问题是：以绘图窗口代替可交互窗口、把暂时取不到窗口当成窗口关闭，以及把搬移/调用成功当成用户可见且可操作。不同应用和不同生命周期让这些假设分别失效。后续补丁在没有统一状态模型和完整验收的情况下叠加，导致一个场景改善、另一个场景退化。

通用方向是建立以真实窗口身份为中心、具有生命周期管理和结果验证的唤起流程；不是继续增加固定延迟、按应用名分支或更换一个私有函数。通用流程可以一致处理状态，但不能承诺所有第三方应用在所有状态下都零跳转。

## 证据与根因边界

详细历史见 [verification.md](verification.md)。以下区分观察、推断和未确认问题。

| 问题 | 已有证据 | 能确定的结论 |
| --- | --- | --- |
| 选择错误窗口 | Lark 的 193 是 AX main/focused 标准窗口；204 为 AXUnknown；1223 在 CG 列表但不在当时 AXWindows 中。它们可以有相同尺寸。实测搬移了 1223，193 留在原桌面，随后用户跳到 193 所在桌面 | 面积、层级和 Space 归属不足以识别主窗口；同尺寸不代表重复的有效主窗口。1223 的具体用途未知 |
| 激活对象不一致 | 移动正确的 193 后，应用级 activate 的测试仍跳桌面；指定窗口激活的一次真实测试和安装后 Space+D 测试成功 | 需要把同一窗口身份贯穿搬移与激活；单次成功不能证明全部生命周期稳定 |
| 窗口身份暂时不可读 | 微信 AX main/focused 返回 noValue、AXWindows 为空时，CG 仍有 440；后来 AX 又能读到 440。Lark 也出现空列表 | “AX 没有结果”不等于“用户关闭了窗口”；CG 有记录也不等于窗口可交互 |
| 失败发生在激活之前 | 用户报告“没有跳转也没有出现”时，验证器提示找不到主窗口，记录未进入 move/show | 该次失败属于身份获取，添加焦点事件无法解决它 |
| 验证假阳性 | 旧验证器只比较结束时 Space 和 CG onscreen；用户仍报告跳转或未显示 | 结束状态不能排除中途跳转，onscreen 不能证明输入焦点及未被遮挡 |
| 设置无法打开 | 用户报告失败；后续读取时可打开且监听已启用；主线程采样是正常事件循环等待 | 尚未捕获设置入口故障，不能断言由 AX 阻塞导致；必须独立验证窗口隐藏、最小化、跨桌面重开 |

需要纠正两点：第一，后续微信窗口编号变化期间，进程也从 3952 变成 25481，不能据此证明同一进程持续重建窗口。第二，初版双按钮检查器曾把两个按钮都接到 Lark，纠正前的结果不能作为微信验收；纠正后同桌面成功仍不算跨桌面成功。

`openApplication(activates=false)` 在暂时没有 AX 窗口时会被调用，这是代码事实；它是否导致每一次跳转，尚无完整事件证据。某次末尾 Space 变化也缺少用户输入归因，不能直接认定是程序回跳。最后用户报告 Dock 也打不开微信，其确切进程/窗口原因仍未确认。

## 为什么不同应用表现不一致

应用进程、AX 可交互窗口、CG 绘图记录是不同对象，不能一一对应。一个应用可能有多个标准窗口、辅助窗口、关闭后保留的进程以及随状态变化的 AX 暴露结果。微信和 Lark 的实现差异会改变窗口枚举与恢复时机，但当前证据不足以归因于某个具体框架。

现有实现把这些差异压成“找到窗口 / 没找到窗口”。于是：重新打开可能干扰尚存窗口；删除 reopen 又会使真正关闭的窗口无法恢复；缓存旧窗口可能补上短时读取失败，也可能引用已经失效的进程或窗口。这是不同补丁互相抵消的原因。

## 尚未解决的工程问题

1. AX 查询把 noValue、超时、失效对象、权限错误等都折叠成 nil，无法选择正确恢复动作。
2. 候选缓存主要按 PID 保存身份，缺少完整的进程世代、窗口销毁和重建失效管理。CG 的 PID/层级/Space 校验不足以证明缓存 AX 仍有效。
3. 候选版本容忍部分 AX 失效后继续按数字窗口 ID 激活，尚未证明安全可靠；0.1/0.3 秒补充 Raise 也不是完整状态同步。
4. 请求按应用分别管理，不足以表达快速交替唤起不同应用时“最后一次操作优先”。桌面变化也没有充分区分用户切换和程序引发的切换。
5. 使用单一 active Space，尚未定义双显示器下目标显示器及桌面的完整语义。
6. 外部 AX 查询存在同步等待；需要隔离以避免影响设置与快捷键响应，但目前没有证据证明它就是设置故障根因。
7. 9 项窗口筛选检查、20 项核心测试和构建通过，不覆盖真实第三方窗口的创建、关闭、恢复、焦点与跨桌面全过程。
8. 测试器与正式快捷键入口不同、候选包复用版本号、频繁替换签名，增加诊断混淆及反复授权成本。

## 通用方案

### 1. 分开两种用户意图

普通启动器负责未勾选当前桌面唤起的绑定，遵循系统应用打开行为。当前桌面窗口控制器负责已勾选绑定，禁止失败后悄悄回退到会跳桌面的普通激活。共享配置与快捷键入口，避免共享含糊的恢复分支。

### 2. 建立窗口身份与生命周期管理

使用 AXObserver 观察主窗口、焦点、窗口创建/销毁，并结合应用启动、退出、隐藏状态和有界重新查询。通知可能缺失，观察结果仍需读回验证。

身份至少包含 bundle、PID、进程启动世代、CGWindowID、AX 引用及窗口世代。进程退出、重启或身份失效后废弃旧引用；不跨启动持久化裸窗口编号。AX main/focused/标准窗口提供语义，CG/Space 只作为交叉校验。存在多个正常窗口时使用明确的最近用户交互目标，而非面积排序。

查询结果必须区分：有效窗口、暂时不可读、对象已销毁、权限不足、接口不支持。空 AX 列表本身不能认定窗口关闭，也不能直接触发 reopen。

### 3. 用状态流程完成一次唤起

流程：捕获目标显示器/桌面与请求编号 → 识别进程和窗口 → 按状态恢复或创建 → 搬移 → 读回窗口身份与 Space → 激活同一窗口 → 验证结果 → 成功、明确失败或取消。

| 状态 | 处理原则 |
| --- | --- |
| 已有有效窗口 | 直接处理该窗口，搬移和激活保持身份一致 |
| 应用隐藏或窗口最小化 | 分别取消隐藏/最小化，重新确认窗口与桌面，不能假定这些操作无副作用 |
| 暂时读取失败 | 在有界时间内等待状态通知并重读；不能当作关闭，也不无限重试 |
| 确认无可恢复窗口或应用未运行 | 进入独立的窗口创建流程；创建行为可能由应用自行控制，尚未验证时不能保证零跳转 |
| 权限失败或能力不支持 | 返回具体原因，停止会改变桌面的后续动作 |
| 用户改变操作意图 | 取消旧请求，不抢回焦点，也不强行把桌面切回 |

全局最新请求优先，跨应用取消旧任务。每个异步步骤重新核对请求、进程/窗口世代和目标桌面；不能仅在最开始检查一次。等待基于状态变化与总时限，避免不断增加固定延迟。

成功必须确认：目标窗口身份仍有效、归属目标桌面、未隐藏/最小化、可见且焦点属于目标窗口；全过程追踪桌面，检测中途跳转。无法充分确认时返回“未确认”，不能报成功。CG onscreen 只是其中一个信号，不能代替完整结果。

### 4. 隔离系统能力与设置界面

把 AX 查询、Space 搬移、指定窗口激活封装成可替换的系统后端。参照成熟项目的完整生命周期与失效处理，不只复制一个私有函数。特定应用适配只有在复现证明通用流程确有缺口时才添加，且不得绕过统一成功条件。

设置窗口拥有独立的打开路径：取消隐藏、恢复最小化、移动到当前桌面、成为可操作窗口；保留菜单与应用重新打开入口。第三方应用 AX 等待不应阻塞设置界面。对设置入口独立测试，避免将其错误混进微信/Lark 的修复。

目标显示器建议以触发时用户操作上下文确定，一次请求内固定；具体选择规则需在双屏验收前明确。全屏 Space 首先标明不支持，不套用普通桌面搬移。

### 5. 明确能力边界

第一阶段只承诺已经识别的、普通桌面上的现存标准窗口。关闭后恢复、冷启动、重启、无 AX 窗口、全屏等路径分别验收，再扩大支持范围。

macOS 第三方 Space 搬移依赖非公开能力，不能仅凭现有实现承诺对所有应用普适。失败时保持操作边界并提示原因；普通方式打开可作为用户主动选择，不能静默替代“当前桌面唤起”。不修改全局设置来掩盖问题，不恢复触控预测隐藏方案。

## 实施顺序与验收门槛

1. 冻结现有实验，保留失败记录。先建立唯一构建编号/提交指纹，记录实际运行的安装路径，避免候选包和安装版混淆。
2. 建立统一诊断记录与可重放后端测试：请求编号、构建指纹、阶段、PID、窗口世代、AX 错误、Space 与时间；不记录标题、聊天内容或触点轨迹。覆盖选错窗口、AX 暂时为空、进程重启、缓存失效、请求交错、移完但未聚焦等真实失败模式。
3. 保持普通启动器行为，独立修复和验证设置重开，再替换当前桌面唤起流程。不要直接把今日全部缓存与延迟实验合并为正式实现。
4. 使用同一不可变候选构建和正式快捷键路径，联合验收微信、Lark；Chrome 普通模式作为行为隔离对照。验证器只观察，不通过重开目标应用改变状态。
5. 两个普通桌面双向重复至少 10 轮；覆盖隐藏、最小化、红色关闭、退出重启、快速交替快捷键、用户主动切桌面与双显示器。每个生命周期单独记录结果；任何错误跳桌面、无窗口却报成功、旧请求抢焦点均判失败。现存窗口阶段未覆盖的恢复路径必须明确标注，不能算整体通过。
6. 通过上述门槛后再安装、发布。改进稳定的开发/发布签名，减少更新后反复授权；不绕过 macOS 身份验证。测试通过与正式签名安装后的权限验收分开记录。

目前完整的、可无人值守复现跨应用生命周期故障的反馈循环尚未建立。这是下一次实现前必须补齐的条件；本报告不是修复完成声明。
